Leer un error y depurar: el traceback es la pila escrita en texto

Cuando un programa se rompe, Python no solo se queja: te deja una nota con qué pasó y dónde, marco por marco. Ese bloque de texto, el traceback, es la misma pila de llamadas que ya conoces, congelada en el instante del fallo. Lo vas a leer con un programa pequeño que calcula el promedio de las notas de cuatro alumnos inventados: uno termina bien y tres se rompen de maneras distintas.

Antes de empezar, piénsalo tú. Cuando un programa se rompe y escupe un bloque de texto rojo, ¿qué parte lees primero y por qué? ¿Crees que la línea que señala el error es siempre la que hay que arreglar? Escribe lo que haces hoy, aunque sea "lo copio y lo busco".

Parte 1 · Paso a paso

De una cadena que se detiene al mensaje de R

Siete pasos. Cada uno termina con un chequeo: hasta que no lo resuelves, el siguiente queda cerrado. Equivocarte aquí no resta nada, es parte del método.

Paso 1

Una cadena de encargos que se detiene

Un programa es una cadena de encargos. Alguien pide un informe de un alumno; el informe le pide a otra pieza que saque el promedio; el promedio suma las notas y después divide entre cuántas notas hay. Cada pieza confía en que la anterior le pasa algo con sentido.

En el escenario ves las tres estaciones y una ficha esperando al inicio: luis. Luis está en la lista de alumnos, pero todavía no tiene ninguna nota. Cuando algo falla, la cadena no se detiene "en general": se detiene en una estación concreta, y ese lugar es la primera pista.

Predice antes de tocar

Paso 2

La última línea dice qué pasó

Ahora la cadena tiene código. En el escenario está el programa (16 líneas) y lo que Python imprimió al correrlo con nombre = "luis": primero la línea alumno: luis, que demuestra que el programa sí arrancó, y después un bloque que empieza con Traceback (most recent call last):.

Ese bloque tiene dos clases de renglones. Los pares File "programa.py", line N, in f seguidos de una línea de código, y un único renglón final que no se parece a los demás. La línea final está tapada a propósito: decide primero dónde buscarías el tipo de fallo.

Las marcas ~~~~~~^~~~~~ debajo de algunas líneas existen desde Python 3.11: subrayan la parte exacta de la expresión que falló. En los tracebacks del libro no aparecen porque son de una versión anterior.

Elige y explica

Paso 3

Las de arriba dicen dónde: cada par es un marco

Cada par File ..., line N, in f es un marco de la pila, el mismo dibujo de la página "Funciones y el marco de llamada". Van en el orden en que se apilaron: arriba el más externo (<module>, el programa principal), abajo el más reciente, justo encima de la línea del qué. Por eso el título dice most recent call last: lo más reciente, al final.

Toca un renglón del traceback y mira qué caja de la pila y qué línea del programa se encienden. O pulsa Leer de abajo hacia arriba: primero el qué, después dónde falló, quién llamó a esa función y quién llamó a esa otra.

Un detalle del libro: en la página 49 del PDF el encabezado dice Traceback (innermost last), el título que usaban las versiones viejas de Python. Más adelante en el mismo libro, y en el Python 3 de hoy, dice Traceback (most recent call last). Mismo orden, otro título.

Ahora se activan los nombres del escenario. Elige uno, pulsa Ejecutar y mira cómo crece la pila marco a marco.

Paso 4

Dónde falla no es dónde está la causa

El traceback te lleva al lugar donde el programa ya no pudo seguir. Eso es el síntoma. La causa puede estar antes: en los datos que llegaron, o en la función que los mandó. Think Python lo dice con todas las letras: el mensaje marca dónde se descubrió el problema, que no siempre es donde se originó.

Una confusión muy común

"La línea que marca el error es la que hay que arreglar"

Mira el escenario: el traceback de luis apunta a la línea 9, return total / len(lista). Antes de tocar nada, decide.

Predice antes de arreglar

La línea 9 está bien escrita: divide la suma entre la cantidad de notas, que es justo lo que es un promedio. Lo que no se cumplió fue una suposición: que la lista traería al menos una nota. El libro trae un ejemplo con la misma forma, en el que la línea señalada no tiene nada mal.

¿Qué es una precondición?

promedio supone que la lista no está vacía. Esa suposición es su precondición: lo que tiene que ser cierto al entrar para que la función haga bien su trabajo. Think Python propone revisar las precondiciones al entrar a una función y las postcondiciones al salir, para saber de quién es la culpa: si la precondición no se cumple, el error es de quien llamó.

Una versión con guarda decide qué hacer con la lista vacía:

Python
def promedio(lista):
    if len(lista) == 0:
        return None
    total = 0
    for x in lista:
        total = total + x
    return total / len(lista)

p = promedio([])
print(p)
print(p + 1)
None
TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'

La guarda evita el ZeroDivisionError, pero devolver None solo mueve el problema a quien use el resultado: el error aparece una línea más abajo, con otro nombre. Decidir qué significa "promedio de nada" es una decisión del programa, no de la línea 9.

Paso 5

Tres familias: no arranca, se detiene, miente

Antes de leer un error conviene saber de qué familia es, porque cada una se busca distinto:

  • Sintaxis: Python ni siquiera empieza. Lee el archivo entero antes de correr y encuentra algo mal escrito.
  • Ejecución: el programa arranca y se detiene a mitad con un traceback. Los del paso 3 son de esta familia.
  • Semántico: el programa termina sin quejarse y entrega algo equivocado. No hay mensaje que leer.

El escenario trae tres tarjetas con su programa y su salida real. Asigna cada una a su familia en el chequeo de abajo. Un detalle de versión: el libro dice que el mensaje típico de sintaxis es SyntaxError: invalid syntax; Python 3.13 ahora es más concreto y dice, por ejemplo, SyntaxError: expected ':'.

Elige y explica

La trampa de este paso: el mismo programa del promedio es un error de ejecución en Python y un error semántico en R. Con luis, Python lanza ZeroDivisionError; R calcula 0/0, devuelve NaN y sigue como si nada. Con pepe, Python da KeyError; R devuelve NULL al buscarlo y termina en NaN. Que un lenguaje no se queje no significa que el programa esté bien.

Paso 6

El estado del programa en el instante del fallo

El traceback dice qué y dónde, pero no siempre por qué. El porqué está en las variables de cada marco en el momento del fallo. En el escenario corre ahora eva, cuyas notas son [10, "6"]: la segunda nota es un texto. Toca cada caja de la pila para abrir sus variables. Las de promedio se destapan cuando resuelvas el chequeo.

Que Python no convierta "6" en 6 por su cuenta es lo que viste en "Tipos y coerción". R sí convierte, pero al revés: en c(10, "6") el 10 se vuelve texto, así que en R eva falla antes, en la primera vuelta.

Mirar dentro sin prints

No hace falta llenar el programa de print. En Python, una línea breakpoint() dentro de la función (o correr el archivo con python -m pdb programa.py) detiene el programa y te deja escribir nombres de variables, subir y bajar por los marcos con up y down, y avanzar línea por línea con n. Es este mismo escenario, pero sobre tu código real.

En R, browser() dentro de una función hace lo mismo. Y en la consola interactiva, justo después de un error, traceback() imprime la pila. Ojo: con Rscript no sirve, porque el script ya terminó cuando lo pedirías. Por eso la vida real de esta página usa otra vía en R.

Paso 7

El mismo error contado por R

El escenario pasa a R con eva. R lo cuenta en tres líneas y en otro orden. La primera, Error in total + x : ..., junta el dónde (la expresión exacta, total + x) y el qué (el texto después de los dos puntos). La segunda, Calls: informe -> promedio, es la pila, escrita en una sola línea de afuera hacia adentro, de izquierda a derecha. La tercera, Execution halted, solo avisa que el script se detuvo. Toca las tres zonas del mensaje.

Los mensajes de esta página salieron en inglés. Si tu R está configurado en español, el mismo error dice "argumento no numérico para un operador binario".

Los errores de R que verás primero son de nombres: si llamas a una función antes de definirla, R contesta que no la encuentra. ISLR2 lo muestra justo antes de escribir su primera función. En el material de la materia hay otro error de R a la vista: seq(20, 2, 2) responde wrong sign in 'by' argument, porque por posición el 20 entra como inicio y el 2 como final.

El material de la UD1 no trae una sección sobre errores ni sobre depuración. Los cuadernos de clase sí muestran errores reales, como ValueError: Table 'ordenes' already exists al crear dos veces una tabla: ahora puedes leerlos con este método.

      Parte 2 · En la vida real
      
Así funciona en la vida real

      
El mismo programa del recorrido, con las mismas notas inventadas, recorre los cuatro nombres. Esta vez no se rompe: cada fallo se atrapa con try/except en Python y con tryCatch en R, y el programa escribe su qué y su dónde. En Python el dónde sale de recorrer la pila guardada en el error con un bucle explícito, y al final se compara con la función de la librería que formatea el error. Los dos lenguajes no fallan en los mismos sitios: por eso cada uno tiene su propia secuencia de líneas ejecutadas. Al cambiar de lenguaje, la animación vuelve a empezar.

En la práctica: lee la última línea (qué), sube por los File ..., line N hasta el primer marco que sea tu propio código (dónde), y mira las variables de ese marco (por qué). La función de librería que hace el trabajo de las líneas pila y donde es traceback.print_exc(), que imprime el traceback completo sin detener el programa. En R no hay una línea equivalente dentro de tryCatch que no meta marcos internos de R (sys.calls() dentro de withCallingHandlers trae cosas como .handleSimpleError); por eso las líneas pila y for marco solo existen en Python, y en R el dónde sale de conditionCall(e), la expresión que falló. El Calls: informe -> promedio del error sin atrapar, que viste en el paso 7, es lo que en R hace el papel de la pila. Los mensajes de R salieron en inglés.


    

      Atrapar solo lo que esperas
      

        
except Exception atrapa todo, también lo que no esperabas. Si solo esperas la lista vacía, nombra esa excepción: lo demás sigue rompiendo el programa, como debe.

        

          
Python
def promedio(lista):
    return sum(lista) / len(lista)

for v in [[7, 9, 8], [], [10, "6"]]:
    try:
        print(promedio(v))
    except ZeroDivisionError:
        print("lista vacia")
8.0
lista vacia
TypeError: unsupported operand type(s) for +: 'int' and 'str'

          
R
promedio <- function(lista) {
  if (length(lista) == 0) stop("lista vacia")
  sum(lista) / length(lista)
}
r <- tryCatch(promedio(c()), error = function(e) conditionMessage(e))
print(r)
x <- tryCatch(as.numeric("8,5"), warning = function(w) conditionMessage(w))
print(x)
[1] "lista vacia"
[1] "NAs introduced by coercion"

        

        
En R, stop("lista vacia") falla a propósito con tu propio mensaje (lo que en Python sería raise), y tryCatch(..., warning = ...) convierte un aviso en algo que puedes ver y manejar. Python Workout usa el mismo patrón para no romperse cuando el usuario escribe algo que no es un número: un try alrededor de int(...) con except ValueError.
