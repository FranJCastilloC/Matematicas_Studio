ORM, DAO y el problema N+1

Un programa casi nunca habla con la base de datos escribiendo SQL a mano en cada pantalla: usa una capa de acceso que convierte tablas en clases y consultas en métodos. Esa comodidad esconde un riesgo. Un código que se ve limpio y da el resultado correcto puede lanzar una consulta por cada fila y ahogar a la base sin que lo notes. Vas a cargar una pantalla de pedidos de una tienda en línea, a contar cuántas consultas lanza y a ver cómo se arregla.

Antes de empezar, piénsalo tú. Una pantalla muestra la lista de pedidos de una tienda y, en cada fila, el nombre del cliente que lo hizo. Los pedidos y los clientes están en dos tablas distintas. ¿Cuántas veces crees que el programa tiene que preguntarle a la base para armar esa pantalla? Escríbelo como te salga, aunque esté mal.

Parte 1 · Paso a paso

De una pantalla a una consulta por fila

Siete pasos. Cada uno termina con un chequeo: hasta que no lo resuelves, el siguiente queda cerrado. Equivocarte aquí no resta nada, es parte del método.

Paso 1

La pantalla de pedidos con el nombre de cada cliente

Una tienda en línea tiene una pantalla que lista sus pedidos y, junto a cada uno, el nombre del cliente. El programa lo arma así: primero le pide a la base la lista de pedidos; después, para escribir cada fila, le pregunta quién es el cliente de ese pedido. Cada pregunta que viaja a la base se llama consulta, y cada viaje de ida y vuelta tiene un costo.

La tienda es la del ejercicio de la UD2: 5 clientes y 6 pedidos (el pedido 5001 es de Marta, el 5002 de Javier, el 5003 otra vez de Marta, y así). A la derecha está la pantalla, todavía vacía. Haz tu predicción y se abrirá el botón para cargarla, una consulta a la vez.

¿Por qué no pedir los clientes antes y ya?

Se puede, y es justo la solución de los pasos 5 y 6. Lo que hace el programa de este paso es lo más natural cuando escribes: «para cada pedido, dame su cliente». El problema no es un error, es que ese estilo no se ve caro en el código y sí en la base.

Predice antes de tocar

Paso 2

Un ORM convierte tablas en clases y consultas en métodos

Un ORM (mapeo objeto-relacional) te deja trabajar con los datos como si fueran objetos del lenguaje y oculta gran parte del SQL. Cada tabla se representa con una clase y cada fila con una instancia de esa clase .

A la derecha está el ejemplo del material, hecho a mano: una línea con objetos y el SQL que le corresponde. Cambia el campo, el operador o el valor y mira cómo cambian las dos. El material solo muestra este par de líneas: el SQL real que genera un ORM más grande no aparece en la unidad.

¿El ORM «sabe» SQL o solo lo escribe por ti?

Solo lo escribe: debajo de todo ORM sigue habiendo consultas SQL que viajan a la base. Lo que cambia es que tú ya no las ves. Esa es la ventaja (menos SQL manual, código más legible) y también el inconveniente: menos control sobre el SQL generado. Por eso el material dice que, con consultas complejas o mucho volumen, a veces conviene SQL directo o una mezcla. Al final de la página, en la parte de vida real, escribes un ORM diminuto a mano para ver que no hay magia.

Calcula con los datos en vivo

Paso 3

El DAO: todo el SQL de una tabla vive en un solo lugar

Con o sin ORM, el código de acceso a datos suele ordenarse con un patrón. El más simple es el DAO (Data Access Object): una clase por entidad con todas las operaciones sobre ella (obtener, guardar, eliminar). Hay dos parientes: el Repository, parecido pero pensado en colecciones de objetos del dominio, y el Active Record, donde el propio objeto sabe guardarse .

Elige un patrón a la derecha. La aplicación solo escribe una llamada; el SQL, con un marcador ? para el valor, vive dentro del DAO. Fíjate en que el contador de «líneas de SQL en la aplicación» no sube nunca. Esa separación es la primera de las buenas prácticas de la unidad . Los valores viajan aparte del texto (parametrizados): ese es el tema de la página de inyección SQL.

El DAO también puede esconder el problema

Un DAO ordena el código, pero no decide cuántas veces lo llamas. Si obtener está bien escrito y tú lo llamas dentro de un bucle, cada vuelta lanza una consulta. Ese es el paso siguiente.

Elige y explica

Paso 4

Pedir el cliente dentro del bucle: N + 1 consultas

Vuelve a la pantalla del paso 1, ahora con las palabras exactas. Para mostrar N pedidos con el nombre del cliente, el programa lanza 1 consulta para la lista y 1 más por cada pedido para su cliente: N + 1 consultas, cuando una sola con JOIN habría bastado. El material lo llama el problema N+1 y dice que es típico de las aplicaciones con ORM .

Aquí $C$ es el número de consultas, $N$ los pedidos en pantalla y $t$ lo que tarda cada consulta (cada viaje a la base). Mueve $N$ y $t$ en la escena. Con 6 pedidos casi no se nota; con 40 o con 4.000, sí. El tiempo es simulado: la escena supone que todas las consultas cuestan lo mismo, y la unidad no trae ninguna medición.

Una advertencia sobre el material: el resumen de la UD5 dice que la unidad trata «el problema N+1» (y también la gestión de credenciales, las migraciones y el mapeo de tipos), pero la UD5 no tiene ningún apartado sobre eso . El N+1 está en la UD4, en el apartado de rendimiento de consultas. Por eso la página lo explica desde ahí.

¿Y si cada consulta abre su propia conexión?

Sería todavía peor. El material dice que abrir una conexión es costoso y que las aplicaciones serias usan un pool: un conjunto de conexiones ya abiertas que se reutilizan . El pool abarata el viaje, pero no quita las N consultas: cada una sigue siendo una ida y vuelta.

Calcula con los datos en vivo

Paso 5

La salida: una sola consulta con JOIN

La solución del material es pedirle a la base que haga la unión: una consulta que trae cada pedido con el nombre de su cliente. Un JOIN empareja cada fila de pedidos con la fila de clientes cuyo id_cliente coincide . Cómo funciona por dentro un JOIN está en la página «Producto cartesiano y JOIN».

Cambia la escena entre uno por uno y JOIN. La pantalla se ve igual: los mismos nombres en las mismas filas. Lo único que cambia es cuántas veces viajaste a la base. La consulta de la escena añade ORDER BY para que el orden sea siempre el mismo: sin él, el orden de las filas no está garantizado.

Elige y explica

Paso 6

Otras dos salidas, y una trampa del JOIN

El JOIN no es la única forma de bajar de N + 1. Hay dos más, que el material no trae y que son comunes:

En lote. Pides los pedidos y, en una segunda consulta, todos los clientes que hacen falta de golpe con WHERE id_cliente IN (...): son 2 consultas, sin importar cuántos pedidos haya. Con memoria. Sigues pidiendo un cliente por vuelta, pero si ya lo pediste antes lo reutilizas: son 1 + d consultas, con $d$ los clientes distintos.

Prueba los cuatro modos en la escena. Fíjate en la columna id_cliente: en los 6 pedidos solo hay 4 clientes distintos (Marta y Javier se repiten), y por eso la memoria ahorra consultas.

Calcula con los datos en vivo

Una confusión muy común

Si el JOIN trae todo en una consulta, ¿por qué no unir todo con todo?

Cuando se aprende el JOIN, la tentación es unir también las líneas de cada pedido (lineas_pedido) «ya que estamos». Los 6 pedidos tienen 9 líneas en total. Esto tampoco está en el material de la unidad.

Predice

Paso 7

En un ORM real: carga perezosa y carga ansiosa

Los ORM esconden el N+1 con una comodidad: al leer p.cliente.nombre, el objeto pide el cliente en ese momento si todavía no lo trajo. Se llama carga perezosa y es lo habitual por defecto. La solución es pedirle al ORM una carga ansiosa de esa relación, para que la traiga de una vez, con un JOIN o con un lote IN. Los nombres cambian según el ORM (en SQLAlchemy son joinedload y selectinload; en Django, select_related y prefetch_related), pero la idea es la misma.

Esto tampoco viene en el material: la unidad dice que el N+1 es típico de los ORM, pero no muestra ningún ORM concreto ni cómo evitarlo. En la escena, el código de abajo es ilustrativo y no está ejecutado; lo que sí se simula es la cuenta de consultas con los mismos datos.

Si al principio escribiste una hipótesis, vuelve a leerla ahora.

Entonces, ¿ORM o SQL directo?

No hay una respuesta única, dice el material. Un ORM te ahorra escribir y mantener SQL, y tiene un costo: puedes lanzar sin darte cuenta un N+1. Quien lo usa bien mira cuántas consultas lanza cada pantalla, como hace la escena, y en los casos delicados escribe el SQL a mano.

      Un mini ORM a mano: ver que no hay magia
      
      
        
      Un ORM, en pequeño, es una clase que arma el SQL por ti. Este reproduce la línea de la Figura 1 del material (filter(precio > 100)). El nombre del campo y el operador no se pueden mandar como parámetro, así que se comprueban contra una lista blanca: es la técnica de la Tabla 5 del material para nombres de columna dinámicos. En Python:
      
        
      import sqlite3

class Consulta:                                        # un mini ORM: arma el SQL con filter
    CAMPOS = {"id_producto", "nombre", "categoria", "precio", "stock"}
    OPERADORES = {">", "<", ">=", "<=", "="}
    def __init__(self, tabla):
        self.tabla, self.condiciones, self.valores = tabla, [], []
    def filter(self, campo, op, valor):
        if campo not in self.CAMPOS or op not in self.OPERADORES:
            raise ValueError("campo u operador no permitido")    # lista blanca
        self.condiciones.append(campo + " " + op + " ?")
        self.valores.append(valor)
        return self
    def sql(self):
        return "SELECT * FROM " + self.tabla + " WHERE " + " AND ".join(self.condiciones)
    def todos(self, con):
        return con.execute(self.sql(), self.valores).fetchall()

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE productos (id_producto INTEGER PRIMARY KEY, nombre TEXT, categoria TEXT, precio REAL, stock INTEGER)")
con.executemany("INSERT INTO productos VALUES (?, ?, ?, ?, ?)", [(101, "Teclado mecánico", "Periféricos", 79.90, 120), (102, "Monitor 27\" 4K", "Monitores", 349.00, 45), (103, "Ratón inalámbrico", "Periféricos", 29.90, 200), (104, "Disco SSD 1TB", "Almacenamiento", 89.50, 80), (105, "Webcam HD", "Periféricos", 39.90, 60), (106, "Router Wi-Fi 6", "Redes", 129.00, 30)])
q = Consulta("productos").filter("precio", ">", 100)
print(q.sql(), "con", q.valores[0])
print(" | ".join(fila[1] for fila in q.todos(con)))
q2 = Consulta("productos").filter("categoria", "=", "Periféricos")
print(q2.sql(), "con", q2.valores[0])
print(" | ".join(fila[1] for fila in q2.todos(con)))

      productos <- data.frame(id_producto = 101:106, nombre = c("Teclado mecánico", "Monitor 27\" 4K", "Ratón inalámbrico", "Disco SSD 1TB", "Webcam HD", "Router Wi-Fi 6"),
                        categoria = c("Periféricos", "Monitores", "Periféricos", "Almacenamiento", "Periféricos", "Redes"),

campos <- c("id_producto", "nombre", "categoria", "precio", "stock")
operadores <- c(">", "<", ">=", "<=", "=")
filtro <- function(tabla, campo, op, valor) {          # un mini ORM: arma el SQL y lo aplica
  if (!(campo %in% campos) || !(op %in% operadores)) stop("campo u operador no permitido")
  sql <- paste0("SELECT * FROM ", tabla, " WHERE ", campo, " ", op, " ?")
  cmp <- if (op == "=") `==` else match.fun(op)
  list(sql = sql, valor = valor, filas = productos[cmp(productos[[campo]], valor), ])
}
q <- filtro("productos", "precio", ">", 100)
cat(paste(q$sql, "con", q$valor), "\n", sep = "")
cat(paste(q$filas$nombre, collapse = " | "), "\n", sep = "")
q2 <- filtro("productos", "categoria", "=", "Periféricos")
cat(paste(q2$sql, "con", q2$valor), "\n", sep = "")
cat(paste(q2$filas$nombre, collapse = " | "), "\n", sep = "")
